# Paragon PR7-V: notes for Claude

This repository starts as a copy of **Paragon PR7-G** (the guitar processor, repo `ARYEZ/Paragon-X1`), full history included, at PR7-G **0.32.1**. It is to become **Paragon PR7-V**, the **vocal** processor. A third sibling, **Paragon PR7-B** (bass, repo `ARYEZ/Paragon-PR7-B`), started the same way.

Everything below describes how the project is built, tested and released, and how the owner likes to work.

## First: make it its own plugin (do this before anything else)

**Done in 0.1.0** (plugin code `Pr7v`). Kept as a record of what makes PR7-V separate from PR7-G.

Until these are done, PR7-V *is* PR7-G as far as a DAW is concerned. The two would replace each other and share rigs and settings.

## The project

- An AGPLv3 **JUCE VST3** plugin: a vocal multi-effects chain, drawn as a floor processor with an expression pedal. No amp or cabinet: PR7-G's NAM amp and IR loader (and the NAM, Eigen and AudioDSPTools dependencies) were removed in 0.3.0 at the owner's request. JUCE is the only dependency. No latency, except while HARMONY's CORRECT (TUNE VOICE) is on: then a fixed 40 ms, reported to the host (the owner's choice).
  - Three finishes in SETTINGS → FINISH: Pearl White, Pearl White + Neon, Pearl Black (see `source/ui/Finish.h`).
- **The chain:** INPUT → LOW CUT → PITCH → (WAH pedal) → DYNAMICS (comp/gate) → DE-ESSER → FILTER/PITCH → GLITCH (Pre) → SATURATION (drive) → PRESENCE → TALK BOX → GRAPHIC EQ → GLITCH (Post) → HARMONY → VOCODER → DOUBLER → MOD → DELAY → REVERB → LO-FI → OUTPUT (+ volume pedal) → LIMITER. Mono up to the EQ, stereo from the DOUBLER on. LOW CUT (under INPUT) and LIMITER (under OUTPUT) are global like INPUT and OUTPUT.
- **The seven stomps** (the owner's order): top row **1 DYNAMICS, 2 SATURATION, 3 DOUBLER**; bottom row **4 PITCH, 5 MODULATION, 6 DELAY, 7 REVERB**. PITCH stays first in the *sound* (it tracks the clean voice best) though its stomp is 4; its stomp switches HARMONY, the octaver and TUNE VOICE (`harmonyCorrect`; since 0.21.1: TUNE VOICE works without HARMONY, so without this the stomp's light went out while the voice stayed tuned and 40 ms late, and PITCH seemed stuck on). `Footswitch` remembers each parameter's value (0-1), not just on/off, so TUNE VOICE comes back in its mode. FREEZE has its own switch. The DYNAMICS stomp switches the compressor and the de-esser (`compOn`, `deessOn`); the de-esser has its own DE-ESS block and panel in the strip (the DYNAMICS panel had no room). The other blocks (FILTER/PITCH, GLITCH, EQ, LO-FI) are in the signal-chain strip only. The display names are the owner's; parameter IDs keep their PR7-G names (`compOn`, `driveOn`...), as IDs never change.
- **Master LIMITER** (0.4.0): under OUTPUT, not a stomp; no look-ahead, so still no latency. Keep it that way.
- **De-esser** (0.5.0): split-band, after the compressor; FREQUENCY, AMOUNT, LISTEN (plays only what's removed).
- **HARMONY** (0.6.0, stage 1 of the owner's goal: "as close as we can get to Waves Harmony"; they sent its user guide). On the PITCH stomp (stomp memory: brings back what was on, first press HARMONY). `effects::Harmony`: PSOLA, formant-preserving; pitch read from the clean voice (after LOW CUT, a voice-range `PitchDetector`), voices made from the processed voice at the start of the stereo section. Key/scale (`Scales.h`, global like Waves' lock), 8 voices (`hv1Pitch`...), correction rule "a third stays a third" (our design), CORRECT FORMANT, SPREAD, SOURCE/HARMONY. `HarmonyPanel`: Waves-style graph. Voices lag ~2 pulses (8-25 ms); the dry voice has no latency (unless CORRECT is on, below).
  - **Stage 2, CORRECT** (0.17.0, `harmonyCorrect`, v38; shown as TUNE VOICE in the panel header): Off / Natural / Hard pitch correction of the singer's voice to the nearest key/scale note (Chromatic scale for any song), by the same PSOLA slices. Natural glides (60 ms), Hard jumps (3 ms); a note is held until another is 0.2 st nearer. Works with HARMONY off. The owner chose a fixed, host-reported delay: while on, the plugin runs `Harmony::correctLatencySeconds` (40 ms) late; the processor's timer calls `updateLatency()` (setLatencySamples from the message thread) and only then does the audio thread switch (`correctLatency`), so reported and actual always agree; voices then use the same fixed delay, in time with the voice. The guide's NOTES state is not built (needs Generate Notes / MIDI). Rigs: A08 Tuned Lead, E21 Hard Tune.
  - **Stage 3, GENERATE NOTES + CHORD maps** (0.19.0, v40: `harmonyGenerate`, `harmonyChord`, `harmonyMinNote`, `harmonyTolerance` (above 200 = Off), `harmonyToleranceTime`, `harmonyNoteLevel/Width/Formant/Attack/Release`; CORRECT gained "Notes"): `Harmony::generateNotes` holds a note until the voice is past TOLERANCE cents for TIME (silence ends it); the root goes into the key, then each `Harmony::chordMaps` interval through `Scales::harmonyNote`. 18 maps, ours (append only). Note voices: their own pool of 8 (Waves shares eight between fixed and note harmonies), exact notes (glide 30 ms), per-sample attack/release, panned by pitch across WIDTH. Panel: NOTES tab after 1-8; note voices drawn blue on the graph. Snapshot `PARAGON_SNAPSHOT_HARMONYNOTES=1`. Our choices: TIME in ms only (default 100 ms; Waves' default is a synced 1/2 note), TOLERANCE Off = only a silence starts a note. Not built: the per-key Note Map Editor, Spread/Fold, synced TIME. Rig E22 Auto Choir.
  - **Stage 4, MIDI notes** (0.20.0, `harmonyMidiMap` v41: As Played / Through Chord): `Harmony::MidiKeys` (velocity per key, sustain pedal) kept by the processor (`harmonyMidi`, read in processBlock beside MARS's MIDI). `generateNotes` gathers the wanted notes (MIDI keys first, then the generated chord, up to 8, deduped), keeps each voice on its note while still wanted, gives new notes the most-faded free voice, pans by pitch rank. Velocity gain 0.3 + 0.7v (ours). CORRECT Notes: the nearest held key in the nearest octave, else the generated note. Panel: MIDI dropdown in NOTES; keyboard strip C2-B5 on the graph (held pink, generated blue; `setMidiKeys`); graph 150 wide in NOTES. Snapshot `PARAGON_SNAPSHOT_MIDI=60,64,67`.
  - **Stage 5, the Note Map Editor** (0.21.0, v42): CHORD map 19 `Custom` (`Harmony::customChord`, the last: append only) and SCALE `Custom` (`Scales::Scale::custom`). The map: per note class a 47-bit mask (bit b = offset b-23, `mapSpan`/`mapBits`) in three 16-bit hidden parameters `harmonyMap{1-12}{A,B,C}` (`ParamIDs::harmonyMap (note, part)`), plus `harmonyMapFold` (Spread/Fold: Fold plays from `foldOctave` 60 + the note class). Keyed by the *sung semitone* (not put into the key first), so an out-of-key note has its own row; each mapped note then goes through `Scales::nearest`. FOLD moves a note an octave nearer while it's more than `maxShift` (24, the voices' 0.25-4 ratio clamp) from the sung note (our choice). Custom scale: `harmonyScaleNote1-12` (In/Up/Down, relative to KEY), global (`notInRigs`), `Scales::Custom` / `customNote`. The processor caches the parameter pointers (no string lookups on the audio thread). `NoteMapEditor` (ui/) is an overlay in `HarmonyPanel` opened by EDIT (`openNoteMap`: CHORD → Custom, copying the current built-in map in if the Custom map is empty); `fillFromChord` matches the engine exactly (a test checks every map, key and scale). Snapshot `PARAGON_SNAPSHOT_NOTEMAP=1` (with `PARAGON_SNAPSHOT_HARMONYNOTES=1`). Not built: per-note velocity/level, named saved maps.
  - **Stage 6, per-voice DELAY/FEEDBACK/FILTER and FLATTEN** (0.22.0, v43; the guide's Harmony Panel and Notes Panel): appended to `harmonyVoiceParts` ("Flatten", "Note" 24-72 default 48 = C3, "Delay" 0-1000 ms (0 Off), "Sync" `Delay::syncNames`, "Feedback", "Filter" `Harmony::filterNames` LP/HP/BP, "Cutoff" 20 Hz-20 kHz default 20 kHz); the note voices share `harmonyNoteDelay/Sync/Feedback/Filter/Cutoff`. `Harmony::Fx` per voice, `VoiceFx` per voice state: TPT state-variable filter (12 dB/oct, skipped when LP at 20 kHz or HP at 20 Hz), then a delay line (2 s, `maxEchoSeconds`; time glides ~30 ms; loop gain `feedbackAtFull` 0.97 x FEEDBACK), all before level/pan. The processor turns SYNC into ms (`harmonyFx`, `getTempoBpm`). Note voices keep running while their echo rings (`VoiceFx::ringing`); a fixed voice switched off clears its echo. FLATTEN in `readPitch`: NOTE (into the key with the voice's CORRECT) + FINE, PITCH ignored. Panel: FLATTEN switch (PITCH knob becomes NOTE), FX toggle after NOTES (`showFx`, `bindFxControls`, `updateVisibility`; picking a filter type that would silence moves CUTOFF), flattened markers show the note name; graph 196 wide in the voice view. Snapshot `PARAGON_SNAPSHOT_HARMONYFX=1`. Not the guide's: SYNC 1/64t-1 bar (ours is `Delay::syncNames`).
  - **Stage 7, GLOBAL** (0.26.0, v44; the guide's Global Controls): `harmonyGlide` (1-1000 ms, default 1 = straight to the note), `harmonyGlideSync` (`Delay::syncNames`; the processor turns it into ms at the tempo), `harmonyGlobalPitch` (-12..+12 st), `harmonyGlobalFormant` (-12..+12 st); `Settings::glideMs/pitch/formant`. Fixed voices glide their absolute pitch (`VoiceState::glidedNote`, reset between notes; GLIDE is the time to arrive, tau = GLIDE/3) after GLOBAL PITCH; note voices glide at max(30 ms, GLIDE/3); GLOBAL FORMANT adds to each voice's. The singer's voice isn't moved (our reading). Panel: GLOBAL button beside the HARMONY switch (`showGlobal`, exclusive with FX; a voice tab or NOTES leaves it), view = GLIDE/SYNC/PITCH/FORMANT over the mix row; "GLOBAL*" when non-default; `updateReadings()` (the timer's work, called by snapshots). Snapshot `PARAGON_SNAPSHOT_HARMONYGLOBAL=1`. Tests: PITCH moves fixed and note voices but not the singer, global FORMANT = the voice's own, GLIDE read from the voice's shift (`getRatio`: a pitch can't be read off a slide).

Saved in rig files (`HarmonySnapshot` children; older plugins ignore them, file version unchanged) and in the project state (a `HarmonySnapshots` child added in getStateInformation, read and removed in setStateInformation); part of `captureRig`/`applyRig`, so undo covers them (`Snapshot::operator==` compares them). ## Build, test, check

- **Build:** `cmake -B build && cmake --build build -j8`.
- **Tests (Catch2):** `xvfb-run -a build/tests/ParagonX1Tests`. All must pass. New features get tests that check what the feature really does to the sound (levels, frequencies, harmonics, pitch), not just that it runs.
- **macOS can differ:** CI tests on Apple Silicon with Apple clang. In 0.10.0 every delay test failed there only (Linux gcc/clang, Windows and the sanitizers were clean): the first channel's echo came out at 0 through a small per-sample lambda choosing -1/+1 (FLIP). Rewritten as a plain per-side gain array, it passed. Prefer plain arrays/values over lambdas in per-sample loops, and when CI fails on one platform only, add a test that records the values (CAPTURE) rather than guessing. 0.10.0 was never published; 0.11.0 carries it.
- **pluginval:** `xvfb-run -a <pluginval> --strictness-level 10 --validate-in-process "build/ParagonX1_artefacts/Release/VST3/<name>.vst3"`. Check its **exit code**, not just "SUCCESS". CI runs it too.
  - **Check where a crash happened before calling it the flake** (0.26.0: a local exit 139 was rerun without looking, and CI then crashed in "Fuzz parameters" before SUCCESS; 14 local seeded runs under gdb, `--random-seed n`, only ever showed the flake's backtrace). The session can't re-run CI jobs (403), so the next push is the re-run.

## Releases

- Bump `project(ParagonX1 VERSION x.y.z)` in CMakeLists.txt and add a matching `## x.y.z` section at the top of CHANGELOG.md, then push.
- CI builds Windows, macOS and Linux and publishes a GitHub Release with the three zips, using that changelog section as the notes.
- After pushing, check the release published (all three zips) about 15 minutes later, **and that its tag points at your commit**: CI skips publishing a version that already exists, so if another session released the same number first, yours silently isn't published (0.18.0: AEON was released first; GENERATE NOTES went out as 0.19.0). Before bumping, fetch main and take the next number after anything released.
- The owner installs from GitHub Releases on **Windows** and works in **BeatMaker**.

## How the owner likes to work

- **Explain the why**, specifically: what was wrong, what changed, and the trade-offs. Plain language; the owner is a musician, not a DSP engineer.
